# PaiCLI 第三章：记忆与上下文

对应教程 `docs/articles/build-agent-p3-memory.md` 的「10、跑起来看看」。这一章是“此前没有接入过”的验收案例：插件核心不包含任何第三章逻辑，全部由外层 Agent 按本文和教程操作。

## 目标

在真实 PaiCLI 里核对：初始长期记忆为空、上下文统计可见、创建项目、按原话保存 JDK 17、`/clear` 之后仍能检索到这条记忆、保存冲突版本被拒绝、`/context` 正常。自动压缩的各个分支不在这次短案例范围内，不能宣称全测。

## 准备

- 当前工作区是 PaiCLI 仓库根目录，本机有 Java 17+、Maven。
- 先在 PaiCLI 仓库根目录构建，再新建本次专用实验目录，复制 jar 并在其中启动；用独立的 `-Duser.home` 保存记忆和会话记录，避免影响个人数据。
- 模型配置只从本机现有 `.env` 或环境变量读取；报告、截图、事件日志里都不要出现密钥。

## 步骤

1. `paiwarp_open`，`record: true`。先 `mvn clean package`，再在实验目录启动 jar。
2. 输入 `/memory`，截图 `memory-empty`；确认长期记忆为空。
3. 输入 `/context`，截图 `context-initial`；记录实际 Token 数和阈值。
4. 输入 `帮我创建一个 Java 项目叫 myapp`，等 PaiCLI 完成；截图 `create-project`。
5. 原样输入 `JDK 可以保持 17，你记一下`。等 PaiCLI 调用 `save_memory`；核对磁盘上的 `long_term_memory.json` 确有这条事实（实际文字可能与教程示意不同，按实际报告）。
6. 输入 `/clear`，再输入一条依赖项目上下文的普通任务（例如“继续检查 myapp 的项目结构”）。核对新的模型请求里含长期记忆里的 JDK 17，且旧短期对话已经清掉；截图 `recall-after-clear`。
7. 输入同一句话，只把 17 改成 21：`JDK 可以保持 21，你记一下`。核对冲突检测拒绝写入，提示由用户决定；不要强制覆盖旧事实。截图 `conflict`。
8. 输入 `/context`，截图 `context-final`，记录压缩阈值和当前占用。
9. 输入 `/exit`，等回到 shell，再 `paiwarp_close`。

## 核对

- `/memory` 初始为空，`save_memory` 之后磁盘文件里确有 JDK 17 这条记忆。
- `/clear` 之后的新请求包含 `## Project Context`（或等价栏目）里的记忆，且不再包含清空前的短期对话。
- 冲突版本没有写入磁盘，旧事实仍在。
- 所有“模型说了什么”的结论都要有会话记录、磁盘文件或请求上下文作证；只有终端回显不算。
- 截图覆盖上述阶段；录屏从启动到退出。

## 已知实测失败

2026-11-11 的真实运行中，第一次保存 JDK 21 被拒后，内层 Agent 自行使用替换参数覆盖了旧值。因此不能只检查第一次工具拒绝；要检查整轮结束后的磁盘事实。保留失败，不自动恢复旧值重跑，不因此把插件传输成功写成业务成功。
